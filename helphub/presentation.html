Slide 3 of 15 • Problem Statement

Problem Statement & Community Challenges

Analysis of real-world bottlenecks identified in existing community communication channels
🚨
1. Fragmented Communication in Crises
In acute emergencies (blood donation, medication shortages, vehicle breakdowns, elderly assistance), SOS posts get lost under non-urgent chit-chat in social media groups with zero spatial categorization.
🛡️
2. Rampant Spam & Lack of Verified Trust
WhatsApp and Telegram groups suffer from anonymous accounts, fake fundraisers, and malicious spam. Requesters have no way to verify the background or safety of respondents before inviting them for help.
🧩
3. Underutilized Local Skills
Skilled neighbors (programmers, electricians, teachers, medical students) are eager to volunteer spare hours, but have no structured platform to advertise their capabilities or locate nearby requests.
🔄
4. Zero Request Lifecycle Tracking
Once an emergency request is resolved, the post remains open, wasting volunteer time. There is no status tracking, no mutual accountability, and no feedback mechanism to reward honest helpers.
Slide 4 of 15 • Objectives

Objectives of the Project

Clear functional, technical, and social goals achieved by the HELPHUB platform
🎯
Functional Goals
  • Enable users to post and discover requests with 4 urgency tiers.
  • Publish ongoing volunteer skill offers.
  • Facilitate private real-time chat with read receipts.
  • Track requests from Open to In Progress to Completed.
🧠
Algorithmic Goals
  • Calculate a dynamic 0-99% match score using Haversine distance.
  • Tokenize required skills vs helper competencies.
  • Weight candidate rating and past volunteer history.
  • Deliver real-time ranking without database latency.
🔒
Safety & Trust Goals
  • Protect phone numbers via in-app chat.
  • Enforce mutual 1-5 star reviews post completion.
  • Prevent review duplication via database constraints.
  • Empower admins with real-time audit telemetry.
Engineering Goal
Build a Dual-Backend Architecture (PHP 8/MySQL & Python 3/SQLite) ensuring 100% portable zero-dependency execution across any operating system.

Slide 6 of 15 • Proposed System

Proposed System & Key Advantages

Architecture of the proposed end-to-end mutual aid ecosystem and its advantages
🚀
The 5-Step Lifecycle Workflow
  • 1. Publish: User creates categorized request with urgency tier.
  • 2. Smart Match: Algorithm scores local helpers dynamically.
  • 3. Coordinate: Requester opens private chat without phone leaks.
  • 4. Execution: Helper completes assistance; status marked Completed.
  • 5. Mutual Trust: Both parties exchange 1-5 star reviews & points.
⭐
Key System Advantages
  • Structured Accountability: Status transitions audited in database.
  • Geo-Spatial Awareness: OpenStreetMap visual markers (Green/Red/Yellow).
  • Fraud Prevention: Reviews unlocked only on task completion.
  • Gamification: Badges (New Helper, Trusted Helper, Community Hero).
  • Moderation: 1-click user blocking and admin abuse queues.
Slide 7 of 15 • Technology Used

Technology Stack & Development Tools

Modern full-stack technologies utilized across frontend, backend, database, and dev tooling
🎨 Frontend Presentation
  • HTML5: Semantic modern document layout.
  • CSS3: Variables design system, Light/Dark modes.
  • Vanilla JavaScript (ES6+): Clean, zero bloated libraries.
  • Fetch API: Asynchronous AJAX without page refresh.
  • Leaflet.js: Interactive mobile-friendly OpenStreetMap.
⚡ Backend Controllers
  • Stack A (Enterprise): PHP 8.1+ with PDO prepared statements.
  • Stack B (Standalone): Python 3 native HTTP engine.
  • RESTful API: Standardized JSON responses (/api/*.php).
  • Security: Bcrypt password_hash and password_verify.
  • Session Auth: Token-based session management.
🗄️ Relational Database
  • MySQL 8.0+: Production relational database.
  • SQLite 3: Portable embedded ACID storage.
  • Normalization: 17 tables structured in 3NF.
  • Integrity: Foreign keys with CASCADE constraints.
  • Uniqueness: Composite keys preventing review spam.

Slide 9 of 15 • System Design

System Design & Architectural Diagrams

Layered architecture, entity relationships (ER), and data flow diagrams (DFD)
3-Tier Layered Architecture
  • Presentation Layer: HTML5 / CSS3 / Vanilla JS / Leaflet Map.
  • API Controller Layer: RESTful endpoints (/api/*.php) routing requests.
  • Business Logic Layer: Haversine math, matching engine, reputation calculator.
  • Data Layer: MySQL / SQLite relational storage with ACID guarantees.
  • Security Interceptor: Role-Based Access Control (RBAC) middleware.
Database Design (17 Tables in 3NF)
  • users: Auth credentials, geo-coordinates, rating, reputation.
  • help_requests & help_offers: Categorized needs, skills, statuses.
  • conversations & messages: Encrypted threads with read status.
  • reviews: Strict UNIQUE(request_id, reviewer_id, reviewee_id).
  • reports & blocked_users: Safety and audit moderation.
State Transition Lifecycle
[Open Request] ➔ [In Discussion] ➔ [Accepted] ➔ [In Progress] ➔ [Completed] ➔ [Mutual Review]

Technical Implementation & UI Highlights

Implementation specifics of key mathematical, database, and client-side mechanisms
Haversine Distance Implementation
d = 2 * R * asin(sqrt(
  sin²(Δφ/2) + cos(φ1)*cos(φ2)*sin²(Δλ/2)
)) [R = 6371 km]

• d <= 5 km: +15 points (Neighborhood)
• d <= 15 km: +10 points (Metro area)
• Same City: +5 points

");
